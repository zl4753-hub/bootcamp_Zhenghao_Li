# Deployment monitoring plan

The service should be monitored across four layers. **Data:** alert the Data Engineering on-call when the daily snapshot is more than one business day stale, required-column schema changes, duplicate dates appear, or any model feature has a null rate above 1%. The first runbook step is to stop scoring, compare the provider payload with the committed schema, and replay from the last valid raw file. **Model:** the Risk Analytics owner reviews a 60-session rolling ROC-AUC and recall weekly. Alert if ROC-AUC falls below 0.55, recall below 0.35, Population Stability Index for a key feature exceeds 0.20, or the alert rate leaves the 10%–45% band for ten sessions. First check data quality and regime mix; retrain only after those checks.

**System:** Platform on-call receives alerts when API p95 latency exceeds 500 ms, five-minute error rate exceeds 2%, or the scheduled pipeline fails twice. The immediate action is rollback to the prior model artifact and serve the last valid score with a stale-data warning. **Business:** the portfolio risk manager reviews alert usefulness, missed high-volatility days, and hedge-review frequency monthly. More than three missed high-volatility days in a rolling month triggers a threshold review.

Retraining occurs quarterly or when a model threshold is breached for two consecutive reviews. Risk Analytics prepares the candidate; the portfolio risk manager approves threshold changes; Platform approves deployment or rollback. Incidents and model changes are logged in the repository issue tracker, with model version, data dates, metrics, approver, and rollback decision.
